# Execution Paths

요청 하나가 흐르는 네 경로. 순서가 곧 우선순위입니다.

```
발화
 │
 ├─ Route ──── hit ───▶ Replay ──── ok ────▶ 완료
 │  Haiku 1회           모델 0회      │
 │  ~300ms                           └─ 셀렉터 miss ─▶ Repair ─┬─ ok ─▶ 재개
 │                                                             └─ fail ─▶ Explore
 └─ miss ────────────────────────────────────────────────────▶ Explore
                                                                 Opus N회
                                                                 └─ 성공 ─▶ 매크로 저장
```

---

## Route — 라우팅

**모델**: Haiku · **비용**: 요청당 1회 · **목표 지연**: 300ms 이하

매크로 레지스트리 목록과 사용자 발화를 대조해 매크로 ID와 파라미터를 뽑습니다.

```
입력   "음악 재생"
출력   { macro: "music-play", params: { track: "음악" } }
```

임베딩이나 벡터 검색은 쓰지 않습니다. 매크로가 수백 개가 될 일이 없고, Haiku 한 번이 더 정확하고 더 쌉니다. 매크로가 100개를 넘어가면 그때 다시 봅니다.

**미스가 정상입니다.** 새 요청은 원래 매크로가 없습니다. 미스를 실패로 취급하지 않습니다.

## Replay — 재생

**모델**: 없음 · **이 프로젝트의 존재 이유**

저장된 스텝을 순서대로 실행합니다.

```
각 스텝:
  1. 셀렉터로 요소 조회        Hands.find(selector)   ~150ms
  2. 있으면 실행               Hands.tap(element)
  3. 없으면 Repair로 에스컬레이션 (그 스텝만)
  4. assert 스텝이면 조건 충족까지 폴링
```

**API로 소켓을 열지 않습니다.** 호출 0회, 토큰 0, 비용 $0은 측정값이 아니라 구조적 사실입니다.

5분을 10초로 만드는 지점이 여기입니다.

## Repair — 자가치유

**모델**: Opus · **비용**: 실패한 스텝당 1~2회

한 스텝의 셀렉터가 안 잡힐 때만 발동합니다. 매크로 전체를 다시 하지 않습니다.

```
입력   현재 화면의 접근성 트리
       실패한 셀렉터와 그 의도 ("검색 버튼을 누르려 했다")
       매크로의 앞뒤 스텝 (맥락)
출력   대체 셀렉터 제안

성공하면 → 매크로 파일에 패치를 써넣고 healedAt 갱신
실패하면 → Explore로 강등
```

**패치를 되쓰는 게 핵심입니다.** 앱이 업데이트돼도 첫 실행만 느리고, 그 다음부터 다시 빨라집니다. 이게 없으면 이 프로젝트는 그냥 매크로 녹화기입니다.

### 화면 밖이면 스크롤이 먼저입니다

셀렉터가 안 풀리는 이유 중 하나는 **컨트롤이 아직 화면에 없는 것**입니다. 접근성 트리는 보이는 것만 담으므로([ADR 0002](adr/0002-ax-tree-over-screenshots.md)) 셀렉터가 틀린 게 아니라 대상이 존재하지 않습니다.

시뮬레이터에서는 드물고 실기기에서는 흔합니다. 진짜 설정은 Apple 계정·업데이트 배너·셀룰러가 위를 차지해서, 시뮬레이터 기준으로 쓴 매크로가 원하는 것이 전부 아래로 밀립니다.

**그래서 복구보다 먼저 스크롤합니다.** 스크롤은 공짜고 복구는 모델 호출입니다.

멈추는 조건은 **횟수가 아니라 화면이 안 변할 때**입니다. 정해진 횟수만큼 미는 방식은 목록이 세 번 전에 끝났어도 계속 밀고, 화면이 그대로라는 건 끝에 닿았다는 뜻입니다. 그때는 컨트롤이 정말 없는 것이고 복구가 다음 차례입니다.

**찾았다고 끝이 아닙니다.** 화면에 있는 것과 누를 수 있는 것은 다릅니다 — 아이폰 14 Pro에서 잰 값으로, 852pt 화면의 y=748에 있는 행은 WDA가 "보인다"고 하고 셀렉터도 풀리는데 **탭이 아무 일도 일으키지 않습니다.** 한 번 더 스크롤해 y=593으로 올리면 같은 탭이 동작합니다. 아래쪽 띠는 홈 인디케이터와 시스템 제스처의 영역이고, 거기 닿은 탭은 앱에 도달하기 전에 삼켜집니다.

그래서 스크롤은 "보일 때까지"가 아니라 **"누를 수 있는 위치까지"** 갑니다.

### 거절해야 하는 복구

고치는 것만큼 **안 고치는 게 중요한** 경우가 있다.

| 상황 | 이유 |
| --- | --- |
| 교체 셀렉터가 **좌표**일 때 | 한 번 되고 다시 깨진다. 그리고 그 스텝이 원래 뭐였는지가 사라진다 |
| 화면에 **비슷한 게 없을** 때 | 아무거나 눌러보는 것보다 실패가 낫다 |
| 안전했던 스텝을 **되돌릴 수 없는 컨트롤**로 고치려 할 때 | 아래 참조 |
| **복구 예산**(기본 2회) 초과 | 스텝마다 고쳐야 하는 경로는 바뀐 게 아니라 없어진 것이다 |

#### 위험 승급은 코드로 막는다

복구는 "사라진 컨트롤과 가장 닮은 것"을 고르는 일이고, **닮음에는 결과에 대한 개념이 없습니다.** 재설계된 화면에서 사라진 `저장` 옆에 `삭제`가 있으면 그게 가장 가까운 후보입니다.

프롬프트에도 적지만 거기서 끝내지 않습니다. 복구는 **매크로에 영구히 써집니다** — 잘못된 계획은 런 하나를 버리지만 잘못된 복구는 그 뒤의 모든 런을, 사람이 안 보는 동안, 이미 안전하다고 승인한 경로에서 망칩니다.

규칙은 한 방향입니다. 원래 되돌릴 수 없던 스텝은 같은 종류로 복구될 수 있습니다 — [승인 게이트](adr/0007-approval-gate-off-device.md)가 이미 앞에 있으니까요. **안전했던 스텝이 그렇게 되는 것만 막습니다.**

실패하고 탐색이 진짜 경로를 찾게 하는 편이, 조용히 취약해진 매크로를 남기는 것보다 낫다.

### 복구 유무를 나란히 잰다

`ScriptedExecutor`(복구 없음)를 지우지 않고 `ReplayExecutor`(복구 있음)와 함께 둔다. **복구가 실제로 뭘 벌어주는지 측정하기 위해서다.** 없으면 "자가치유됩니다"는 주장이지 결과가 아니다.

셀렉터를 존재하지 않는 식별자로 바꾼 매크로로 실기에서 재보면 `0/2` 대 `2/2`가 나온다. `npm run heal`이 그 실험이다 ([벤치마크](benchmarks/2026-09-09-self-healing-live.md), [journal](journal/2026-09-09-self-healing.md)).

## 했다는 말은 증거가 아닙니다

탐색이 `done` 이라고 하면, **화면을 따로 읽어서 확인합니다.**

[ADR 0009](adr/0009-runner-judges-not-executor.md)가 성공 판정을 러너에게 맡겼지만, 그 러너는 eval 에만 있었습니다 — 사람이 쓴 검증 기준이 담긴 태스크 파일이 있고 `falseClaims` 를 셉니다. 실사용 경로는 모델의 말을 그대로 믿었습니다.

실제로 이렇게 틀렸습니다. 유튜브 뮤직에서 "추천 노래 하나 틀어줘" 를 시켰더니 곡까지 가서 플레이어에 **`재생` 버튼** — 누르면 시작되는 그 버튼 — 을 띄워놓고 done 이라고 했습니다. 마지막 한 걸음을 안 하고 성공이라고 한 것입니다.

**끝난 화면에서 뽑은 기준으로는 판정할 수 없습니다.** 그 화면에서 뽑아 그 화면에 대고 검사하면 구성상 항상 통과합니다. 요청과 화면을 놓고 따로 읽어야 합니다.

그건 [ADR 0006](adr/0006-model-tiering.md)이 이미 싼 티어에 배정해둔 역할입니다 — *"지금 화면이 재생 중인가"는 분류 문제입니다.* 구현이 없었을 뿐입니다.

**판정자에게 런의 이력은 주지 않습니다.** 주면 자기가 만든 이야기를 검토하게 되고, 그게 확인이 필요했던 바로 그 부분입니다. 요청과 화면이 입력의 전부입니다.

판정 기준도 한 방향입니다 — **화면이 결론을 내주지 않으면 아니오**입니다. 실패로 보고된 런은 다시 찾으면 되고 그건 조금 비쌉니다. 잘못된 성공은 저장되어 반복됩니다.

## 승인 게이트

되돌릴 수 없는 동작은 **묻기 전에는 실행되지 않습니다.**

| risk | 동작 |
| --- | --- |
| `safe` | 그냥 실행 |
| `confirm` | 게이트에 묻고, 승인 없으면 실행 안 함 |
| `blocked` | 묻지 않고 거절 — 이미 내린 결정을 매번 흥정하게 만들지 않습니다 |

`risk`는 매크로를 추출할 때 **누른 컨트롤의 이름**으로 판정합니다 — 무엇을 하려 했는지보다 실제로 무엇을 눌렀는지가 나은 증거입니다.

### 기본값은 거절입니다

게이트를 지정하지 않은 호출자는 승인한 적이 없는 호출자입니다. 채널이 없으면(`DenyingGate`), 터미널이 없으면(cron·파이프), 시간이 초과되면, 알 수 없는 답이 오면 — 전부 거절입니다. **승인하는 유일한 경우는 사람이 `승인`이라고 타이핑한 때**입니다. 엔터만 눌러서 도달할 수 없게 일부러 단어로 두었습니다.

### 무엇을 누르는지 말합니다

"이 경로는 위험합니다"는 누구도 의미 있게 승인할 수 없습니다. "이 경로는 **삭제**를 누릅니다"는 승인할 수 있습니다. 그래서 요청에는 위험 등급이 아니라 **컨트롤 이름**이 들어갑니다.

### 게이트가 있는 곳

지금은 맥의 터미널입니다. 폰 화면이 아닌 것이 핵심입니다 — WDA가 폰 화면을 조작하므로, 거기 그려진 승인 버튼은 **에이전트가 스스로 누를 수 있습니다**([ADR 0007](adr/0007-approval-gate-off-device.md)).

relay와 Live Activity가 본래 채널이고, 터미널은 ADR이 명시한 폴백입니다. 인터페이스가 같아서 relay 구현이 들어올 자리는 이미 있습니다.

## Explore — 탐색

**모델**: Opus · **비용**: 스텝당 1회 · **소요**: 1~5분

매크로가 없는 새 요청. 풀 에이전트 루프입니다.

```
반복:
  1. 화면 관찰      Hands.screen()  → 압축된 트리
  2. 다음 액션 결정  Opus            → 액션 1개
  3. 실행           Hands.act()
  4. 종료 조건 확인
```

**한 번에 액션 하나만** 계획합니다. 여러 스텝을 미리 계획하면 첫 스텝 결과가 예상과 다를 때 나머지가 전부 무의미해집니다.

### 컨텍스트 관리

스크린샷과 트리가 누적되면 20스텝 만에 컨텍스트가 터집니다. 두 가지로 막습니다.

- **컨텍스트 편집** (`clear_tool_uses_20250919`) — 오래된 관찰 결과를 서버가 잘라냅니다
- **트리 우선, 스크린샷은 요청 시에만** — 기본 관찰은 300~600토큰짜리 텍스트 트리

### 종료 조건

| 조건 | 처리 |
| --- | --- |
| 목표 달성 | 매크로 추출 → 사용자 승인 → 저장 |
| 3스텝 연속 실패 | 중단. 현재 화면과 함께 사용자에게 보고 |
| 5분 초과 | 강제 중단 |
| 생체인증 요구 | 중단. 사람에게 넘김 |
| 위험 액션 도달 | 승인 대기 (거부 시 중단) |

## 실패 처리 요약

| 실패 | 대응 | Brain이 아는가 |
| --- | --- | --- |
| WDA 세션 사망 | Hands가 재생성 + 멱등 재시도 | 모름 |
| 셀렉터 미스 | Repair | 앎 |
| 3연속 실패 | 중단 + 보고 | 앎 |
| 시스템 알림이 터치를 막음 | `blocked-by-alert`로 보고. 답하는 건 별도 액션 | 앎 |
| 예상 못한 앱 내 모달 | Repair가 "예상 못한 화면"으로 처리 | 앎 |
| 앱 크래시 | 재실행 후 처음부터 (멱등 매크로만) | 앎 |
| 생체인증 | 중단, 사람에게 | 앎 |

## 시스템 알림

iOS의 권한 요청 같은 시스템 알림은 **앱의 접근성 트리에 나타나지 않는다.** 트리는 평범한 화면을 보여주는데 모든 터치는 흡수된다.

그래서 `Screen`에 `alert` 필드를 두고, 터치 계열 액션은 알림이 떠 있으면 `blocked-by-alert`로 실패한다.

**셀렉터 미스와 구분하는 게 핵심이다.** 컨트롤은 거기 있고 셀렉터도 찾았다 — 모달이 터치를 먹고 있을 뿐이다. 이걸 `no-match`로 보고하면 Repair가 멀쩡한 셀렉터를 고치러 간다.

**자동으로 답하지 않는다.** 위치 권한 허용, 알림 허용, 삭제 확인은 전부 되돌릴 수 없는 결정이고, 이건 [ADR 0007](adr/0007-approval-gate-off-device.md)이 승인 게이트를 둔 이유 그 자체다. `answerAlert(button)`은 버튼 이름을 명시해야 하는 별도 액션이고, 트레이스에 남는다.
