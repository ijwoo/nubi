# Execution Paths

요청 하나가 흐르는 네 경로. 순서가 곧 우선순위입니다.

```
발화
 │
 ├─ Route ──── hit ───▶ Replay ──── ok ────▶ 완료
 │  Haiku 1회           모델 0회      │
 │  ~300ms                           └─ 셀렉터 miss ─▶ Repair ─┬─ ok ─▶ 재개
 │                                                             └─ fail ─▶ Explore
 └─ miss ────────────────────────────────────────────────────▶ Explore
                                                                 Opus N회
                                                                 └─ 성공 ─▶ 매크로 저장
```

---

## Route — 라우팅

**모델**: Haiku · **비용**: 요청당 1회 · **목표 지연**: 300ms 이하

매크로 레지스트리 목록과 사용자 발화를 대조해 매크로 ID와 파라미터를 뽑습니다.

```
입력   "음악 재생"
출력   { macro: "music-play", params: { track: "음악" } }
```

임베딩이나 벡터 검색은 쓰지 않습니다. 매크로가 수백 개가 될 일이 없고, Haiku 한 번이 더 정확하고 더 쌉니다. 매크로가 100개를 넘어가면 그때 다시 봅니다.

**미스가 정상입니다.** 새 요청은 원래 매크로가 없습니다. 미스를 실패로 취급하지 않습니다.

## Replay — 재생

**모델**: 없음 · **이 프로젝트의 존재 이유**

저장된 스텝을 순서대로 실행합니다.

```
각 스텝:
  1. 셀렉터로 요소 조회        Hands.find(selector)   ~150ms
  2. 있으면 실행               Hands.tap(element)
  3. 없으면 Repair로 에스컬레이션 (그 스텝만)
  4. assert 스텝이면 조건 충족까지 폴링
```

**API로 소켓을 열지 않습니다.** 호출 0회, 토큰 0, 비용 $0은 측정값이 아니라 구조적 사실입니다.

5분을 10초로 만드는 지점이 여기입니다.

## Repair — 자가치유

**모델**: Opus · **비용**: 실패한 스텝당 1~2회

한 스텝의 셀렉터가 안 잡힐 때만 발동합니다. 매크로 전체를 다시 하지 않습니다.

```
입력   현재 화면의 접근성 트리
       실패한 셀렉터와 그 의도 ("검색 버튼을 누르려 했다")
       매크로의 앞뒤 스텝 (맥락)
출력   대체 셀렉터 제안

성공하면 → 매크로 파일에 패치를 써넣고 healedAt 갱신
실패하면 → Explore로 강등
```

**패치를 되쓰는 게 핵심입니다.** 앱이 업데이트돼도 첫 실행만 느리고, 그 다음부터 다시 빨라집니다. 이게 없으면 이 프로젝트는 그냥 매크로 녹화기입니다.

## Explore — 탐색

**모델**: Opus · **비용**: 스텝당 1회 · **소요**: 1~5분

매크로가 없는 새 요청. 풀 에이전트 루프입니다.

```
반복:
  1. 화면 관찰      Hands.screen()  → 압축된 트리
  2. 다음 액션 결정  Opus            → 액션 1개
  3. 실행           Hands.act()
  4. 종료 조건 확인
```

**한 번에 액션 하나만** 계획합니다. 여러 스텝을 미리 계획하면 첫 스텝 결과가 예상과 다를 때 나머지가 전부 무의미해집니다.

### 컨텍스트 관리

스크린샷과 트리가 누적되면 20스텝 만에 컨텍스트가 터집니다. 두 가지로 막습니다.

- **컨텍스트 편집** (`clear_tool_uses_20250919`) — 오래된 관찰 결과를 서버가 잘라냅니다
- **트리 우선, 스크린샷은 요청 시에만** — 기본 관찰은 300~600토큰짜리 텍스트 트리

### 종료 조건

| 조건 | 처리 |
| --- | --- |
| 목표 달성 | 매크로 추출 → 사용자 승인 → 저장 |
| 3스텝 연속 실패 | 중단. 현재 화면과 함께 사용자에게 보고 |
| 5분 초과 | 강제 중단 |
| 생체인증 요구 | 중단. 사람에게 넘김 |
| 위험 액션 도달 | 승인 대기 (거부 시 중단) |

## 실패 처리 요약

| 실패 | 대응 | Brain이 아는가 |
| --- | --- | --- |
| WDA 세션 사망 | Hands가 재생성 + 멱등 재시도 | 모름 |
| 셀렉터 미스 | Repair | 앎 |
| 3연속 실패 | 중단 + 보고 | 앎 |
| 시스템 알림이 터치를 막음 | `blocked-by-alert`로 보고. 답하는 건 별도 액션 | 앎 |
| 예상 못한 앱 내 모달 | Repair가 "예상 못한 화면"으로 처리 | 앎 |
| 앱 크래시 | 재실행 후 처음부터 (멱등 매크로만) | 앎 |
| 생체인증 | 중단, 사람에게 | 앎 |

## 시스템 알림

iOS의 권한 요청 같은 시스템 알림은 **앱의 접근성 트리에 나타나지 않는다.** 트리는 평범한 화면을 보여주는데 모든 터치는 흡수된다.

그래서 `Screen`에 `alert` 필드를 두고, 터치 계열 액션은 알림이 떠 있으면 `blocked-by-alert`로 실패한다.

**셀렉터 미스와 구분하는 게 핵심이다.** 컨트롤은 거기 있고 셀렉터도 찾았다 — 모달이 터치를 먹고 있을 뿐이다. 이걸 `no-match`로 보고하면 Repair가 멀쩡한 셀렉터를 고치러 간다.

**자동으로 답하지 않는다.** 위치 권한 허용, 알림 허용, 삭제 확인은 전부 되돌릴 수 없는 결정이고, 이건 [ADR 0007](adr/0007-approval-gate-off-device.md)이 승인 게이트를 둔 이유 그 자체다. `answerAlert(button)`은 버튼 이름을 명시해야 하는 별도 액션이고, 트레이스에 남는다.
