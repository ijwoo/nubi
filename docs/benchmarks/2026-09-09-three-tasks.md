# 2026-09-09 — 태스크 3개 베이스라인

[첫 베이스라인](2026-09-09-scripted-baseline.md)은 태스크 하나였다. 하나로는 아무것도 비교할 수 없어서, **상호작용 모양이 서로 다른** 태스크로 늘렸다.

여전히 "학습 전/후" 비교는 아니다. Explore가 아직 API 키를 못 받았다.

## 측정 조건

| | |
| --- | --- |
| 대상 | iOS Simulator (iPhone 17 Pro) |
| OS | iOS 26.4.1 |
| Xcode | Xcode 26.6 |
| WebDriverAgent | 16.12.5 |
| 앱 | 설정 (com.apple.Preferences) |
| 실행기 | scripted — 손으로 쓴 매크로 재생 |
| 반복 | 태스크당 5 |

## 결과

| 태스크 | 모양 | 성공 | p50 | p95 | 액션 | 모델 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| settings-open-accessibility | 목록 → 상세 | 5/5 | 8959ms | 9030ms | 2 | 0 |
| settings-open-about | 2단계 중첩 | 5/5 | 10541ms | 10960ms | 3 | 0 |
| settings-search-open | 포커스 → 입력 | 5/5 | 15337ms | 15552ms | 3 | 0 |

15런 전부 성공, 모델 호출 0회.

## 왜 이 세 개인가

같은 모양을 세 번 재는 건 한 번 재는 것과 다르지 않다. **Explore가 붙었을 때 어디서 갈리는지 보려고** 다른 모양을 골랐다.

- **목록 → 상세** — 가장 단순. 화면에 보이는 걸 한 번 누른다.
- **2단계 중첩** — 첫 화면 변화에서 멈추면 안 된다. 진행처럼 보이는 지점을 지나쳐야 한다.
- **포커스 → 입력** — 순서가 있는 두 액션. 필드를 누르지 않고 입력하면 텍스트가 아무 데도 안 간다.

세 번째가 Explore에게 가장 어려울 것으로 예상한다. 순서를 틀리면 조용히 실패하기 때문이다 — `type`은 성공을 반환하고 텍스트만 사라진다.

## 검색 화면이 느린 이유

15.3초로 다른 둘보다 5~6초 느리다. 트레이스를 보면:

```
act     4650ms  launch
act     3926ms  tap 검색창
act     3678ms  type "손쉬운"
assert  1683ms  텍스트 지우기
assert  1602ms  task assertion
```

키보드가 뜬 화면은 **원시 트리가 321노드 115KB**다(설정 루트는 168노드 61KB). WDA가 그걸 직렬화하는 데 시간이 걸리고, 액션마다 관찰이 두 번씩 들어간다.

**압축은 토큰을 줄이지만 WDA 응답 시간은 못 줄인다.** 우리가 받는 건 여전히 전체 트리다.

## 측정 중에 고친 것 — 키보드

검색 화면 첫 관찰이 **40요소 828토큰**이었다. 예산(600)을 넘었고, 그중 26개가 키보드 자판이었다.

자판은 우리 액션 어휘에서 쓸모가 없다. 타이핑은 `type` 액션으로 포커스된 요소에 가지, 글자를 눌러서 하지 않는다. **모델에게 누를 수 없는 키를 보여주는 건 토큰과 자리를 둘 다 낭비한다.**

`Key` 타입만 제외했다. 커스텀 키패드가 Button으로 그려진 경우는 남는다 — 거기서는 버튼이 정말 유일한 입구다.

```
40요소 828토큰  →  14요소 325토큰
```

그리고 가려져 있던 것들이 드러났다 — 제안 목록의 "손쉬운 사용" 버튼 같은 것들. **노이즈를 걷어내니 실제 컨트롤이 보였다.**
