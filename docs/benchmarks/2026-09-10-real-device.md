# 2026-09-10 — 실기기 첫 측정

지금까지의 모든 숫자는 시뮬레이터에서 나왔습니다. 이건 진짜 아이폰입니다.

## 측정 조건

| | |
| --- | --- |
| 기기 | iPhone 14 Pro (iPhone15,2) |
| OS | iOS 26.6 |
| Xcode | Xcode 26.6 |
| WebDriverAgent | 자체 빌드, `com.<팀>.WebDriverAgentRunner` |
| 연결 | USB + `iproxy 8100` (무선도 응답 확인) |
| 앱 | 설정 (com.apple.Preferences) |
| 모델 | `claude-sonnet-5` (기본, [ADR 0010](../adr/0010-planning-on-sonnet.md)) |

비교 대상인 시뮬레이터는 iPhone 17 Pro / iOS 26.4.1 입니다.

## 식별자는 같았습니다

가장 걱정했던 것 — 시뮬레이터에서 쓴 셀렉터가 실기기에서 안 통하는 것 — 은 **일어나지 않았습니다.**

```
com.apple.settings.general        "일반"
com.apple.settings.accessibility  "손쉬운 사용"
ACCESSIBILITY_PLACARD
```

전부 그대로입니다. [자가치유 실측](2026-09-09-self-healing-live.md)이 "복구의 상한을 잰다"고 적어둔 시험 — 진짜 다른 식별자를 만났을 때 복구가 되는가 — 은 **여전히 못 해봤습니다.** 만날 일이 없었습니다.

## 다른 건 화면 크기였습니다

`npm run live` 가 8개 실패했고, 전부 하나에서 나왔습니다.

실기기 설정의 첫 화면:

```
설정
임재우, Apple 계정, iCloud+ 등
Apple Music 3개월 무료 혜택을 놓치지 마세요.
소프트웨어 업데이트 사용 가능
에어플레인 모드 / Wi‑Fi / Bluetooth / 셀룰러 / 개인용 핫스팟 / 배터리 / VPN
```

**`일반`이 없습니다.** 화면 밖입니다. 시뮬레이터는 계정도 알림도 셀룰러도 없어서 첫 화면에 다 보였습니다.

압축은 화면 밖 요소를 버리므로([ADR 0002](../adr/0002-ax-tree-over-screenshots.md)) 셀렉터가 틀린 게 아니라 **대상이 트리에 존재하지 않습니다.** 손으로 쓴 매크로 셋은 전부 이 이유로 실기기에서 못 돕니다.

## 탐색은 스스로 해결했습니다

```
✓ 탐색  52778ms  $0.0183
```

모델이 만든 매크로:

```json
{ "op": "launch", "bundleId": "com.apple.Preferences", "restart": true },
{ "op": "swipe", "from": [0.5, 0.7], "to": [0.5, 0.3] },
{ "op": "tap",   "sel": { "id": "com.apple.settings.accessibility" } },
{ "op": "assert","sel": { "id": "ACCESSIBILITY_PLACARD" } }
```

**스와이프를 스스로 넣었습니다.** 검증 기준도 손으로 쓴 매크로가 쓰는 것과 같은 `ACCESSIBILITY_PLACARD` 를 골랐습니다.

재생은 3/3, 모델 호출 0회:

| | 실기기 | 시뮬레이터 |
| --- | ---: | ---: |
| 탐색 | 52.8s · $0.0183 | 11.2s · $0.0085 |
| 재생 | 32.1 / 47.1 / 31.8s · $0 | 8.9s · $0 |

## 느린 이유는 관찰입니다

동작별로 재면:

| | 실기기 | 시뮬레이터 |
| --- | ---: | ---: |
| `screen()` 1회 | **2.2s** | ~0.6s |
| tap (내부에 `screen()` 2회) | 10.9s | 2.9s |
| swipe | 8.1s | — |
| launch (restart) | 6.1s | 4.5s |

`screen()` 안을 더 쪼개면:

| | |
| --- | ---: |
| `/source?format=json` | **1569ms** (349 KB) |
| `/wda/activeAppInfo` | 84ms |
| 둘 동시에 | 1692ms |

**트리를 뜨는 1.6초가 전부입니다.** 349KB 를 JSON 으로 직렬화해 케이블로 넘기는 비용이고, 시도해본 것 중 어느 것도 줄이지 못했습니다.

| 시도 | 결과 |
| --- | --- |
| `waitForIdleTimeout: 0`, `animationCoolOffTimeout: 0` | 1814 → 1734ms (4%, 잡음 수준) |
| `snapshotMaxDepth` 50 → 10 | 시간 동일, 요소도 17개로 동일 |
| 세 왕복을 병렬로 | 1737 → 1692ms — `/source` 가 지배해서 의미 없음 |

줄이려면 **더 빠르게가 아니라 덜 자주** 봐야 합니다.

## 덜 자주 보게 했습니다

탐색은 스텝마다 화면을 네 번 읽고 있었습니다.

| | 무엇 | 쓰임 |
| --- | --- | --- |
| A | 루프 상단 `screen()` | 계획에 들어감 |
| B | `tap` 내부 (셀렉터 해석) | 모델 호출 사이에 화면이 바뀌었을 수 있으니 필요 |
| C | `tap` 내부 (액션 후) | 트레이스가 결과 화면 해시로 기록 |
| D | 다음 루프 상단 `screen()` | **C 와 같은 상태를 다시 읽음** |

C 와 D 사이에는 아무 일도 일어나지 않습니다. 액션이 돌려준 화면을 다음 관찰로 이어받게 했습니다.

**단, 액션 전후 해시가 다를 때만** 이어받습니다. 같으면 액션이 아무것도 안 했거나 너무 일찍 읽은 것이고, 둘 다 왕복 한 번을 아끼는 것보다 다시 보는 편이 낫습니다.

| | 전 | 후 |
| --- | ---: | ---: |
| 탐색 (실기기) | 52.8s | **32.0 / 28.9 / 29.1s** |
| 모델 호출·비용 | $0.0183 | $0.0183 / $0.0123 / $0.0129 |
| 찾은 경로 | 동일 | 동일 |

**39% 빨라졌고 모델은 그대로입니다.** 기기를 덜 귀찮게 했을 뿐입니다.

B 는 남겨뒀습니다. A 와 탭 사이에 모델 호출이 2~4초 들어가서 그동안 화면이 바뀔 수 있고, 다시 해석하는 것이 그 대비입니다.

## 화면 밖은 스크롤로 해결했습니다

손으로 쓴 매크로 셋이 실기기에서 못 도는 원인이 "대상이 화면 밖" 하나였으므로, 재생기가 복구를 부르기 전에 스크롤해 찾도록 했습니다. 스크롤은 공짜고 복구는 모델 호출입니다.

```
손으로 쓴 매크로 (시뮬레이터에서 작성, 그대로)
  launch → tap #com.apple.settings.accessibility → assert #ACCESSIBILITY_PLACARD

  스크롤 없음 (scripted)  0/1
  스크롤 있음 (replay)    1/1   51942ms   복구 0회
```

**모델을 한 번도 부르지 않고 통과합니다.**

### 보이는 것과 누를 수 있는 것은 다릅니다

여기서 예상 못 한 게 나왔습니다. 한 번 스크롤하면 `손쉬운 사용`이 y=748(화면 852pt)에 나타나고, WDA 는 보인다고 하고 셀렉터도 풀립니다. **그런데 그 좌표를 탭하면 아무 일도 일어나지 않습니다** — 화면 해시조차 안 바뀝니다.

| | y | 탭 결과 |
| --- | ---: | --- |
| 스와이프 1회 | 748 / 852 (0.91) | 아무 일 없음 |
| 스와이프 2회 | 593 / 852 (0.73) | 열림 |

아래쪽 띠는 홈 인디케이터와 시스템 제스처의 영역입니다. 그래서 스크롤은 "보일 때까지"가 아니라 **"누를 수 있는 위치까지"** 갑니다. 경계값(0.12~0.8)은 이 한 번의 측정에서 나온 보수적인 값이고, 문서화된 숫자가 아닙니다.

이 화면들은 픽스처로 기록해뒀습니다(`fixtures/settings-device/`). 시뮬레이터가 만들 수 없는 상황이라, 폰을 꽂지 않고도 CI 가 이 경로를 계속 검증합니다.

## 전체 측정 — 실행기 셋

`npm run eval -- --executor all --runs 5`, 45런.

| 태스크 | 실행기 | 성공 | p50 | p95 | 모델 | $/런 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| open-about | scripted | **0/5** | 19160ms | 19293ms | 0 | — |
| | replay | 5/5 | 52960ms | 53526ms | 0 | — |
| | explore | 5/5 | 40961ms | 55822ms | 4 | $0.0188 |
| open-accessibility | scripted | **0/5** | 19272ms | 19476ms | 0 | — |
| | replay | 4/5 | 51479ms | 82891ms | 0 | — |
| | explore | 5/5 | 34569ms | 35192ms | 3 | $0.0141 |
| search-open | scripted | 4/5 | 43407ms | 62420ms | 0 | — |
| | replay | 5/5 | 43242ms | 43486ms | 0 | — |
| | explore | 5/5 | 39878ms | 40268ms | 3 | $0.0126 |

합계 $0.227.

**`scripted` 가 두 태스크에서 0/5 입니다.** 스크롤이 없으니 화면 밖 대상을 못 찾고, 매크로가 틀린 게 아니라 대상이 트리에 없습니다. 같은 매크로를 `replay` 로 돌리면 통과합니다 — **모델 호출 0회로**.

세 번째 태스크는 scripted 도 됩니다. 검색창은 첫 화면에 있어서 스크롤할 일이 없습니다. **스크롤이 필요한 경우에만 값을 하고, 필요 없을 때는 아무것도 하지 않습니다.**

`replay` 가 `scripted` 보다 느린 건 스크롤 왕복 때문입니다. 실패한 런을 되살리는 대가입니다.

## 기기가 가끔 크게 느려집니다

실패 두 건이 둘 다 성능 문제였습니다.

**replay / accessibility (82.9s).** 스크롤은 두 번 만에 찾았고 탭도 성공했는데, **그 탭 하나가 35.5초** 걸렸습니다(보통 10초). 이어진 검증이 8초 안에 못 끝나 실패했습니다. p95 가 82891ms 로 p50(51479ms)의 1.6배인 것이 이 한 런입니다.

**scripted / search-open.** `This operation was aborted` — 요청이 30초 제한에 걸렸습니다.

두 번째가 중요합니다. **같은 오류가 직전 측정을 1런 만에 죽였습니다.** 러너의 판정 호출이 try/catch 밖에 있어서, 요청 하나가 abort 되자 나머지 44런은 시도조차 되지 않았습니다. 판정할 수 없는 런은 실패한 런으로 기록하고 넘어가도록 고쳤고, 이번에는 한 런의 실패로 끝났습니다.

실기기는 **평균적으로 느린 게 아니라 가끔 크게 느립니다.** 시뮬레이터에서는 p50 과 p95 가 거의 같았습니다.

## 설정은 가벼운 앱이었습니다

카카오톡을 시켜보고 알았습니다. 관찰 비용은 기기가 아니라 **앱**이 정합니다.

| 화면 | 트리 | `/source` |
| --- | ---: | ---: |
| 설정 | 349 KB | 1.6s |
| 카카오톡 채팅 목록 | 3.4 MB | 28.7s |

3.4MB 는 요청 제한(30초)에 걸려서, 카카오톡은 **아예 조작할 수 없었습니다.**

### 스냅샷 깊이가 여기서는 지렛대였습니다

설정에서는 깊이를 50에서 10까지 낮춰도 시간도 요소 수도 그대로였습니다. 트리가 작아서 잴 것이 없었던 것입니다. 무거운 앱에서는 다릅니다.

| depth | 시간 | 크기 | 압축 후 요소 |
| ---: | ---: | ---: | ---: |
| 50 | 22799ms | 748 KB | 24개 |
| **20** | **1392ms** | **50 KB** | **28개** |
| 12 | 381ms | 15 KB | 7개 |
| 8 | 287ms | 12 KB | 7개 |

**16배 빠르면서 주소 지정 가능한 요소는 오히려 많습니다.** 깊이 50에서 더 내려가며 얻던 것은 레이아웃 뼈대였습니다.

바닥도 분명합니다. 12 에서는 같은 화면이 28개에서 7개로 떨어지고, **그 실패는 조용합니다** — 에러가 아니라 그냥 휑한 화면으로 보입니다. 기본값을 20 으로 잡은 건 그 여유를 두기 위해서고, 설정은 어느 쪽이든 영향이 없습니다.

매크로가 쓰는 셀렉터는 전부 살아남았습니다(`SearchField`, `com.apple.settings.*`). 잃은 것은 제목 텍스트나 오버레이 이미지 같은 장식입니다.

### 대화방은 여전히 못 읽습니다

같은 앱이라도 화면에 따라 다릅니다.

| depth | 시간 | 압축 후 요소 |
| ---: | ---: | ---: |
| 20 | 29893ms | 43개 |
| 12 | 455ms | 7개 |

12 와 20 사이에 절벽이 있고, 그 사이에 쓸 만한 지점을 찾지 못했습니다. **카카오톡 대화방은 현재 방식으로 관찰할 수 없습니다.** 메시지 목록이 깊게 중첩된 탓으로 보이며, 화면 밖 메시지까지 트리에 들어오는지는 확인하지 않았습니다.

## 이 숫자로 말할 수 없는 것

- **기기 하나, 앱 하나, 태스크 하나.** 재생 3회.
- **재생 편차가 큽니다** (31.8~47.1s). 3회로는 p95 를 말할 수 없습니다.
- **스와이프가 들어간 경로가 얼마나 안정적인지 모릅니다.** 3회는 다 맞았지만 관성 스크롤은 매번 같은 곳에 서지 않습니다 — 아래 참조.
- **무선은 응답만 확인했고 실제로 돌려보지 않았습니다.**

## 하마터면 두 번 틀리게 적을 뻔했습니다

**"iOS 26이 일반을 없앴다".** 큰 스와이프(0.7→0.3)로 훑었더니 VPN 다음이 사운드였습니다. 그 사이 일반·손쉬운 사용·알림이 통째로 없는 것처럼 보였는데, **관성으로 건너뛴 것**이었습니다. 작게(0.62→0.42, 900ms) 나누니 다 있었습니다.

이건 기록해둘 가치가 있습니다 — 탐색이 만든 매크로에도 큰 스와이프가 들어 있고, **같은 이유로 언젠가 목표를 지나칠 수 있습니다.**

**"왕복이 9ms".** 만료된 세션에 요청을 보내고 404 응답 시간을 재고 있었습니다. 살아있는 세션에서는 1569ms 입니다.

둘 다 그럴듯한 숫자였고, 둘 다 응답 내용을 확인해서 잡았습니다.
