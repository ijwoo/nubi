# 2026-09-24 — 잠금화면 스파이크

[슬라이스 1](../ios-client-slices.md) 의 설계를 가르는 미확인 둘을 실기기 잠금 상태에서 쟀습니다. 측정용으로 만든 별도 프로젝트였고 **답을 얻은 뒤 지웠습니다** — 코드는 git 기록에 있고, 숫자는 여기 남깁니다.

## 측정 조건

| | |
| --- | --- |
| 기기 | iPhone 18 Pro (`iPhone19,2`) — **개인 폰** |
| OS | iOS 27.0 |
| Xcode | 26.6 (17F113) |
| 설치 경로 | TestFlight 내부 테스트, 빌드 1 과 2 |
| 상태 | **잠금** (잠금화면 스크린샷의 시계와 기록의 분이 일치) |
| 네트워크 | Wi‑Fi, 상대는 `https://example.com/` |

조작 폰(iPhone 14 Pro)이 아니라 개인 폰입니다. [실기기 45런](2026-09-10-real-device.md) 과 기기가 다릅니다.

## 무엇을 물었나

| | 질문 | 답 |
| --- | --- | --- |
| **A** | `LiveActivityIntent` 가 앱을 깨우지 않고 처리되는가. 네트워크를 칠 수 있는가 | **앱을 안 깨움. 네트워크 됨** |
| **B** | 잠금 상태에서 Control 위젯 → App Intent 가 EventKit 읽기/쓰기를 하는가 | **읽기·쓰기 다 됨** |

둘 다 가장 좋은 경우입니다. 설계가 바뀐 것은 답 자체가 아니라 **숫자와 그 옆의 조건**입니다.

## A — 잠금화면 승인 버튼

| 항목 | 결과 |
| --- | --- |
| 버튼을 눌렀을 때 앱이 열렸는가 | **아니오** — 눈으로 확인, 잠금화면에 머묾 |
| Live Activity 가 잠금화면에 떴는가 | 예 |
| 네트워크 | **HTTP 200**, 빌드 1·2 합쳐 13번 모두 |
| 화면이 꺼진 채 2분 뒤에도 동작 | 예 |

### 캐시가 숫자를 3자리 속였다

| | 빌드 1 (기본 캐시) | 빌드 2 (캐시 끔 + URL 에 타임스탬프) |
| --- | --- | --- |
| 첫 호출 | 194ms | 992ms |
| 이후 | 1 · 2 · 3 · 4ms | 775 · 786 · 804 · 844ms, 한 번 **2016ms** |

**1~4ms 는 `URLCache` 였습니다.** `URLSession.shared` 기본 정책이라 같은 URL 이 재사용됐습니다. 진짜 왕복은 **0.8~1.0초이고 2초까지 벌어집니다.**

빌드 1 만 보고 "승인 응답이 즉시 간다" 고 적었으면 설계가 그 위에 얹혔을 것입니다.

### 1초가 비어 있으면 사람이 다시 누른다

인텐트는 `ContentState` 를 건드리지 않습니다. 그래서 누른 사람 눈에는 **아무 일도 일어나지 않습니다** — 고장난 버튼과 구별되지 않습니다.

```
06:54:33  [승인버튼] 시작
06:54:34  [승인버튼] 시작      ← 앞의 것이 네트워크를 기다리는 중에 다시 눌림
06:54:34  [승인버튼] 시작
06:54:35  [승인버튼] 끝 775ms
06:54:35  [승인버튼] 끝 786ms
```

**같은 초에 인텐트가 겹쳐 돌았습니다.** 되돌릴 수 없는 동작에 붙는 버튼에서 이건 중복 승인 경로입니다. 논스로 막을 수 있지만, 두 번 누르게 만드는 것 자체가 결함입니다.

## B — 잠금화면 Control 위젯 → EventKit

| 항목 | 권한 주기 전 | 권한 준 뒤 |
| --- | --- | --- |
| 인텐트가 도는가 | 예 | 예 |
| 일정 읽기 | 권한 거부됨 | **성공 — 2건** |
| 미리알림 쓰기 | 권한 거부됨 | **성공** |
| 대화상자 | 안 뜸 | 해당 없음 |
| 소요 시간 | 21~29ms | 첫 **492ms**, 이후 **65 · 66ms** |

```
06:57:21  [EventKit] 시작 — 일정 전체 허용, 미리알림 전체 허용
06:57:21  [EventKit] 일정 읽기 성공 — 2건
06:57:21  [EventKit] 미리알림 쓰기 성공 / 끝 65ms
```

이 줄들이 **잠금화면 스크린샷과 같은 분**이고, 그 화면 왼쪽 아래 버튼이 스파이크 컨트롤이었습니다. 폰이 잠긴 채 버튼만으로 미리알림이 추가됐습니다.

### 첫 호출은 프로세스를 띄우는 값이다

492ms → 65ms. 7배 차이는 **확장 프로세스가 살아 있느냐**입니다. 사용자가 겪는 것은 대개 첫 번째입니다. 빠른 모드의 "3초 안에 답한다" 를 따뜻한 상태에서 재면 안 됩니다.

### 확장이 권한을 물으면 조용히 거부로 굳는다

**이 스파이크에서 가장 값진 한 줄입니다.**

빌드 2 에 요청 전 상태를 찍는 줄을 넣었더니 `아직 묻지 않음` 이 아니라 **`거부됨`** 이 나왔습니다. 앱은 그때까지 권한을 한 번도 요청한 적이 없고, 대화상자는 뜬 적이 없고, 사용자는 거절한 적이 없습니다.

| 언제 | 상태 |
| --- | --- |
| 아무것도 안 했을 때 | `아직 묻지 않음` (이어야 함) |
| **확장이 요청한 뒤** | **`거부됨`** — 묻지 않고 |
| 앱이 요청한 뒤 | `전체 허용` |

21~29ms 는 **아무것도 기다리지 않았다**는 뜻입니다. 회복은 앱에서 됩니다. 하지만 그 사이 빠른 모드는 "권한 거부" 로 답하고, 사용자는 자기가 거절한 기억이 없으니 설정에서 고칠 생각도 못 합니다.

## 설계로 옮긴 것

[슬라이스 계획](../ios-client-slices.md#확인한-것--스파이크-결과) 에 규칙 셋으로 들어갔습니다.

1. **권한은 앱이 먼저 받는다.** 확장은 상태를 읽기만 하고, 없으면 앱을 열어달라고 말한다
2. **표시를 네트워크보다 먼저 바꾼다.** 보내기 전에 `ContentState` 가 움직여야 한다
3. **속도는 차가운 상태에서 잰다.** 따뜻한 확장으로 재면 7배 좋게 나온다

## 이 스파이크가 답하지 않은 것 (2026-09-25 추가)

**확장이 Live Activity 를 *시작*할 수 있는가는 안 쟀습니다.** 스파이크는 활동을
**앱에서** 띄우고, 확장은 그 위의 버튼을 누르는 쪽만 봤습니다. 그래서 "잠금
상태에서 확장이 돈다" 는 맞지만 "거기서 활동을 띄울 수 있다" 로 읽으면 틀립니다.

슬라이스 1 에서 그 자리가 바로 걸렸습니다. 같은 키가 양쪽에 있는데도 실패가
둘로 갈립니다.

```
[프로세스] 확장 빌드 4, 실시간활동키 있음
[활동] 시작 실패 … Target does not include NSSupportsLiveActivities plist key
[프로세스] 앱 빌드 4, 실시간활동키 있음
[활동] 시작 실패 … Target is not foreground
```

`.ipa` 를 풀어 확장의 Info.plist 에 키가 있는 것을 확인한 뒤였습니다. **앞의 문구는
사실을 말하지 않습니다.** 확장에서는 애초에 안 되는 일이고, 오류가 그렇게 말할
뿐입니다.

갈림은 인텐트의 **종류**입니다.

| | 어디서 도는가 | 활동을 시작할 수 있는가 |
| --- | --- | --- |
| `AppIntent` | 확장 프로세스, 또는 배경의 앱 | **아니오** |
| `LiveActivityIntent` | 앱 프로세스 | **예, 배경에서도** |

스파이크의 승인 버튼이 `LiveActivityIntent` 였던 것은 우연이 아니라 그 이름 그대로의
용도였는데, 그때는 활동이 이미 떠 있어서 차이가 드러나지 않았습니다.
