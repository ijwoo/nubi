# 2026-09-09 — Explore vs 재생

첫 **학습 전/후** 비교다. 지금까지의 벤치마크는 손으로 쓴 매크로만 쟀다. 여기서는 같은 태스크를 두 실행기로 돌린다.

- **explore** — 목표만 주고 모델이 화면을 보며 스스로 찾아간다. 매크로 없음.
- **scripted** — 그렇게 찾아낸 경로를 매크로로 저장해 재생한다. 모델 호출 0회.

[ADR 0003](../adr/0003-macro-replay-without-model.md)이 주장하는 "재생에는 모델이 필요 없다"의 실측 근거다.

## 읽는 법

**재생이 1.3~1.5배 빠르고 비용이 0이다.** 차이가 극적이지 않은 건 두 실행기가 같은 WDA를 쓰기 때문이다. 앱 실행 4~5초, 탭 한 번 1~4초는 양쪽 모두에 붙는다. 모델이 사라져도 기기는 그대로 느리다.

**모델 비용이 태스크당 1.4~2.3센트다.** 하루 20번 쓰는 동작이라면 탐색으로만 굴릴 때 월 $8~14, 매크로로 굳히면 $0이다. 재생이 의미 있는 건 속도보다 이쪽이다.

**액션 수는 explore가 더 적다.** scripted가 3인데 explore가 2인 건 매크로가 `assert`를 액션으로 세기 때문이다. explore는 `done`으로 끝내고 판정은 러너가 한다 ([ADR 0009](../adr/0009-runner-judges-not-executor.md)).

## 예상이 빗나간 곳

[태스크 3개 베이스라인](2026-09-09-three-tasks.md)에서 이렇게 적었다.

> 세 번째가 Explore에게 가장 어려울 것으로 예상한다. 순서를 틀리면 조용히 실패하기 때문이다 — `type`은 성공을 반환하고 텍스트만 사라진다.

**틀린 방향으로 맞았다.** 순서를 틀린 런은 하나도 없었다. 모델은 매번 필드를 먼저 눌렀다. 대신 **눌렀다는 걸 몰라서 한 번 더 눌렀다.**

첫 측정에서 5런 중 2런이 이랬다.

```
계획  tap    — 검색창에 입력하려면 먼저 포커스
실행  tap    ok=True
계획  tap    — 검색 필드에 포커스를 주기 위해 탭     ← 이미 됐는데
실행  tap    ok=True
계획  type   — 검색 필드에 포커스가 있으니 입력
```

관찰에 포커스 정보가 없었다. 탭 전후로 요소도 해시도 그대로라, 모델 입장에서 첫 탭은 아무 일도 안 일어난 것과 구별되지 않는다. 안전한 수는 한 번 더 누르는 것이고, 모델은 그걸 했다.

화면에 키보드 1비트를 실어서 고쳤다 — 자세한 건 [저널](../journal/2026-09-09-focus-invisible.md)에.

| | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| p50 | 21176ms | 23436ms |
| p95 | 32249ms | 24178ms |
| 모델 호출 | 3~4 (흔들림) | 3 (고정) |
| 토큰 | 1993 | 1782 |

p95가 8초 줄고 흔들림이 사라졌다. p50이 오히려 2초 는 건 이 비교가 5런짜리라 그 정도 잡음은 그냥 있다는 뜻이다 — **p50 차이를 신호로 읽으면 안 된다.**

## 이 숫자로 말할 수 없는 것

- **태스크 3개, 앱 1개, 런 5회.** 경향이지 분포가 아니다.
- **모델은 Opus 하나만 쟀다.** [ADR 0006](../adr/0006-model-tiering.md)은 탐색에 Opus를 쓴다고 정해놨지만 아직 근거가 없다. Sonnet·Haiku 스윕이 다음이다.
- **전부 성공한 태스크만 있다.** 실패했을 때 비용이 어떻게 되는지가 실사용에서는 더 중요한데, 여기엔 실패가 없다.
