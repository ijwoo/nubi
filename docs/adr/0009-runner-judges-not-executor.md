# 0009. 성공 판정은 러너가 하고 실행기는 하지 않는다

**상태**: accepted
**날짜**: 2026-09-09

## 맥락

eval 하네스는 같은 태스크를 여러 접근 방식으로 시도하고 비교한다 — 스크립트 재생, 모델 탐색, 자가치유 재생. 각 접근을 `Executor`로 두고 바꿔 끼운다.

누가 "성공했다"고 판정할 것인가.

## 결정

역할을 셋으로 나눈다.

| | 하는 일 |
| --- | --- |
| Task | 목표와 증거를 정의한다. 경로는 정의하지 않는다 |
| Executor | 시도한다. 자기가 끝냈다고 생각하는지 보고한다 |
| Runner | setup, 시간 측정, 그리고 **기기에 assertion을 직접 확인** |

실행기가 주장한 성공과 기기가 확인한 성공이 다르면 `falseClaims`로 집계된다.

## 이유

**실행기가 자기 성공을 판정하면 측정하는 게 실행기의 의견이다.** 특히 Explore는 모델이 "다 했다"고 판단하는 순간 끝나는데, 그 판단이 맞는지가 정확히 측정하려는 대상이다.

Explore가 실제로 하게 될 실수 — 비슷한 화면에 도달하고 목표를 달성했다고 믿는 것 — 는 자기 판정으로는 절대 안 잡힌다.

**태스크에 스텝을 안 넣는 것도 같은 이유다.** 스텝을 태스크에 넣으면 모든 측정이 "누군가 적어둔 스텝"의 측정이 된다. 같은 목표에 다른 방법으로 도달하는 걸 비교하는 게 요점인데.

## 대안

**실행기가 성공을 반환** — 단순하다. 그리고 Explore의 자기 과신을 측정 불가능하게 만든다.

**실행기와 러너가 각각 판정하고 일치할 때만 성공** — 더 엄격하지만, 실행기가 실패를 정직하게 보고한 경우와 성공을 잘못 주장한 경우가 구분되지 않는다. 둘을 따로 기록하는 편이 정보가 많다.

## 결과

실행기는 "끝냈다고 생각한다"만 반환하면 되므로 인터페이스가 얇다.

러너가 assertion 확인에 시간을 쓴다 — 첫 베이스라인에서 741ms다. 이건 측정 구간 안에 있고, 모든 접근에 동일하게 적용되므로 비교에 영향을 주지 않는다.

`falseClaims`가 0이 아닌 접근 방식은 성공률과 별개로 신뢰할 수 없다는 신호가 된다.
