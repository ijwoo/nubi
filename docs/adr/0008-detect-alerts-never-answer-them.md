# 0008. 시스템 알림은 감지하되 자동으로 답하지 않는다

**상태**: accepted
**날짜**: 2026-09-09

## 맥락

액션을 실기에 처음 붙였을 때 tap·click·drag가 전부 HTTP 200을 반환하면서 화면이 안 움직였다. 원인은 이전 세션에서 뜬 위치 권한 알림이 화면을 덮고 모든 터치를 흡수하고 있던 것이었다.

문제는 알림 자체가 아니었다. **알림이 떠 있는 동안에도 `/source`는 앱의 정상적인 트리를 반환했다.** 요소도 다 보이고 셀렉터도 다 찾아지고 탭도 "성공"한다. 에이전트 입장에서는 완벽하게 평범한 화면이다.

## 결정

`Screen`에 `alert` 필드를 두고 관찰할 때마다 확인한다. 터치 계열 액션은 알림이 있으면 `blocked-by-alert`로 실패한다.

**자동으로 답하지 않는다.** `answerAlert(button)`은 버튼 이름을 명시해야 하는 별도 액션이다.

## 이유

**셀렉터 미스와 구분해야 한다.** 컨트롤은 거기 있고 셀렉터도 찾았다 — 모달이 터치를 먹고 있을 뿐이다. `no-match`로 보고하면 Repair가 멀쩡한 셀렉터를 고치러 가고, Opus 호출을 몇 번 태운 뒤 엉뚱한 결론에 도달한다.

**자동 수락은 승인 게이트를 우회한다.** 알림이 묻는 건 위치 권한 허용, 알림 권한 허용, 삭제 확인이다. 전부 되돌릴 수 없고 사용자 계정에 영향을 준다. [ADR 0007](0007-approval-gate-off-device.md)이 승인 게이트를 둔 이유 그 자체를 위반한다.

명시적 액션으로 두면 트레이스에 남고, 나중에 `risk: confirm`으로 게이트를 걸 수 있다.

## 대안

**첫 버튼 자동 클릭** — 가장 쉽고, 이 문제가 영원히 안 보이게 만든다. 그리고 사용자 폰에서 권한을 임의로 허용한다.

**알림을 무시하고 진행** — 지금 상태 그대로다. 탭이 조용히 사라진다.

**Repair에게 맡김** — 모델에게 알림 화면을 주고 판단시킬 수 있다. 하지만 모델은 트리를 보는데 알림은 트리에 없다. 감지 자체가 코드의 일이다.

## 결과

관찰마다 요청이 하나 늘어난다(`/alert/text`). 관찰 요청이 두 배다.

받아들인다. 모달을 못 보는 대가를 실제로 치러봤다. 관찰 비용이 지연을 지배한다는 건 [첫 베이스라인](../benchmarks/2026-09-09-scripted-baseline.md)에서도 드러나므로, 최적화가 필요해지면 알림 확인 빈도를 줄이는 것도 후보가 된다 — 다만 "액션이 실패했을 때만 확인"으로 바꾸면 탐색 중에 모델이 모달을 못 보게 된다.

`FakeHands`에 `showAlert()`를 붙여서 이 경로를 기기 없이 검증한다.
