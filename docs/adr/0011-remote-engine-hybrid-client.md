# 0011. 엔진은 맥에 남기고, 폰은 독립 클라이언트로

**상태**: accepted
**날짜**: 2026-09-24

## 맥락

[온디바이스 이식 조사](../ios-port-study.md)의 결론은 분명했습니다. 서드파티 앱은 다른 앱의 UI 를 조작할 수 없고, App Intents 로도 **다른 앱의 intent 를 직접 부를 수 없습니다** — 조합은 단축어 앱이 하고, 앱이 할 수 있는 것은 URL 로 단축어 앱을 띄우는 것뿐입니다.

그래서 "맥 없이 아이폰 단독"은 **"아무 앱이나"를 포기해야만** 성립합니다. 그건 다른 제품입니다.

한편 지금 물건의 실제 문제는 맥이 필요하다는 것 자체가 아니었습니다. **맥 앞에 앉아 터미널에 타이핑해야 한다**는 것이었고, 맥 앞이면 손으로 하는 게 빠릅니다(실기기 재생 43~53초 대 손으로 5초).

## 결정

**엔진은 맥에 남기고, 폰은 그 엔진의 클라이언트가 됩니다.** 목표를 "맥 없이"에서 **"맥 앞에 앉지 않아도"** 로 바꿉니다.

- 맥 미니를 상시 실행 서버로 두고, **조작 전용 아이폰**을 케이블이나 같은 네트워크로 연결합니다. Hands·Explore·Replay·Repair 는 그대로 여기서 돕니다.
- 폰 앱은 **독립 클라이언트**입니다. 잠금화면 입력, Live Activity·다이나믹 아일랜드 표시, 승인 버튼을 담당합니다.
- 앱은 두 모드로 답합니다.
  - **빠른 모드** — 온디바이스. EventKit 일정·미리알림 조회와 추가, LLM 답변. 맥이 필요 없고 목표는 수 초.
  - **작업 모드** — 맥 미니 경유. 매크로 실행과 탐색. 진행·승인·결과를 푸시로 받습니다.
- 라우팅은 기존 코드 Router 를 그대로 씁니다. 매크로에 매칭되면 작업 모드, 아니면 빠른 모드.

## 이유

**"아무 앱이나"가 이 프로젝트의 주장입니다.** [overview](../overview.md) 가 존재 이유로 적은 것이 *"맥은 이미 셸이 있지만 아이폰은 아무 방법도 없다"* 였습니다. 온디바이스 단독은 자체 앱 기능만 조합할 수 있으므로 그 주장을 지울 수 없습니다.

**불편했던 것은 맥의 존재가 아니라 맥 앞에 앉는 일이었습니다.** 폰이 입력과 승인을 맡으면 그 불편이 사라지고, 엔진은 이미 실기기에서 45런으로 검증돼 있습니다 — 버릴 이유가 없습니다.

**빠른 모드가 대부분의 요청을 받습니다.** "내일 일정 뭐야", "장 보기 미리알림 추가" 같은 것들은 앱 조작이 필요 없고 EventKit 으로 수 초에 끝납니다. 맥까지 왕복하면 관찰 한 번이 1.6~2.5초인 엔진을 불러 30초를 쓰게 됩니다. **작업 모드는 앱을 조작해야만 되는 일에만 씁니다.**

**두 기기로 나뉘면 승인 게이트가 물리적으로 분리됩니다.** [ADR 0007](0007-approval-gate-off-device.md) 은 게이트가 에이전트의 손이 닿지 않는 곳에 있어야 한다고 정했고, 그 근거는 Live Activity 가 XCUITest 의 요소 트리 바깥이라는 것이었습니다. 조작 대상이 별도 기기가 되면 **그 논증이 필요 없어집니다** — 승인은 다른 기기에서 일어납니다.

## 대안

**온디바이스 단독 (자체 앱 intent 만)** — "아무 앱이나"를 포기해야 합니다. 이 프로젝트가 아닌 물건이 됩니다.

**단축어 경유 조합** — 매크로를 단축어로 내보내고 `shortcuts://` 로 실행. 사용자가 직접 고칠 수 있다는 장점이 있지만 **스텝마다 앱 전환이 보이고**, 여전히 단축어가 지원하는 앱에서만 됩니다. 채택하지 않습니다.

**맥 전용 유지** — 지금 상태. 폰에서 시킬 수단이 없어 결국 안 쓰게 됩니다.

**Swift 포팅 / JavaScriptCore** — 온디바이스에서 엔진을 돌리지 않기로 했으므로 검토를 보류합니다. 되살아나는 경우는 단 하나, 위 결정을 뒤집어 온디바이스 단독으로 갈 때입니다.

## 함께 정한 것

**조작 폰은 별도 기기입니다.** 위의 게이트 논증은 이 전제 위에 섭니다. 같은 기기로 합치면 [ADR 0007](0007-approval-gate-off-device.md) 의 원래 논증(Live Activity 는 요소 트리 바깥)으로 돌아가야 합니다.

**빠른 모드의 모델은 API 우선입니다.** 슬라이스 1 의 완료 조건은 *맥이 꺼져도* 이지 *인터넷이 없어도* 가 아니므로 충돌하지 않습니다. 온디바이스 모델은 나중에 오프라인 폴백으로만 봅니다 — Apple Intelligence 지원 기기로 한정되고 한국어 품질이 미확인입니다.

**대상 앱은 여러 기기 동시 로그인이 되는 것부터.** 조작 폰에 실제 계정이 로그인된 채 원격으로 조작되므로, 휴대폰 한 대만 로그인되는 앱은 제외합니다 — 그런 앱을 조작 폰에 넣으면 **개인 폰에서 로그아웃됩니다.** 앱별 위험도는 [대상 앱 검토](../target-apps.md)에서 `shared/risk.ts` 기준에 맞춰 매깁니다.

## 결과

**ADR 0007 의 relay 가 pip-any 가 아닙니다.** 그 ADR 은 *"이미 pip-any 에 relay 와 Live Activity 파이프라인이 있어서 새로 만들 게 거의 없다"* 를 부수적 근거로 들었습니다. pip-any 를 쓰지 않기로 했으므로 **relay 와 클라이언트를 새로 만듭니다.** 게이트를 조작 대상 바깥에 둔다는 결정 자체는 그대로이고, 오히려 기기가 분리되어 더 강해집니다.

**엔진 코드는 바뀌지 않습니다.** 폰은 기존 `nubi run` 이 하던 일을 원격으로 시키는 것이고, Router·Judge·Trace 는 이미 실행기 종류를 모릅니다. [조사 문서 3장](../ios-port-study.md)의 `Surface` 추상화는 **이 방향에서는 필요하지 않습니다** — 실행기가 하나(맥)뿐이므로, 그 제안은 온디바이스 실행기가 생길 때까지 보류합니다.

**새로 지는 짐이 둘입니다.** APNs 키와 푸시 토큰 관리, 그리고 맥 미니가 꺼져 있을 때의 동작. 뒤쪽은 [슬라이스 계획](../ios-client-slices.md)에서 "큐에 쌓지 않고 거절한다"로 정했습니다 — 한 시간 뒤에 실행되는 요청은 그때의 화면에 대해 아무것도 약속할 수 없습니다.

**되돌릴 때 건드릴 곳**: 폰 앱과 relay 는 통째로 버리면 되고, 엔진은 그대로 남습니다. 그게 이 방향을 고른 이유이기도 합니다.
