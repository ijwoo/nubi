# 0004. 셀렉터 우선순위와 좌표를 최후에 두는 이유

**상태**: accepted
**날짜**: 2026-09-08

## 맥락

매크로 스텝은 "어떤 요소를 누를지"를 저장해야 합니다. 저장 방식에 따라 매크로 수명이 결정됩니다.

## 결정

셀렉터를 5단계 우선순위로 두고, 위에서부터 시도합니다. 좌표는 마지막입니다.

```
1. accessibilityIdentifier
2. label + type
3. labelContains
4. index (type 기준 n번째)
5. 정규화 좌표
```

좌표로 탭한 스텝 뒤에는 `assert`를 **의무화**합니다.

## 이유

각 방식이 무엇에 의존하는지가 다릅니다.

| 방식 | 의존 대상 | 깨지는 시점 |
| --- | --- | --- |
| id | 개발자가 붙인 식별자 | 거의 안 바뀜 |
| label | 표시 텍스트 | 문구 변경, 로케일 변경 |
| index | 목록 순서 | 정렬 변경, 항목 추가 |
| 좌표 | 해상도 + 레이아웃 + 스크롤 | 셋 중 뭐든 |

좌표에는 다른 것들에 없는 문제가 하나 더 있습니다. **실패가 조용합니다.**

셀렉터가 안 잡히면 명확한 미스가 나고 Repair가 발동합니다. 좌표는 항상 "성공"합니다 — 그냥 잘못된 곳을 누를 뿐입니다. 그래서 좌표 탭은 반드시 `assert`로 결과를 확인해야 합니다. 확인 없는 좌표 탭은 실패를 성공으로 기록합니다.

## 대안

**항상 좌표** — 구현이 단순하지만 매크로 수명이 며칠입니다. 이 프로젝트의 전제가 무너집니다.

**항상 id만** — 가장 안정적이지만 대부분의 앱이 identifier를 안 붙입니다. 실전에서 커버리지가 너무 낮습니다.

**XPath** — WDA가 지원하지만 DOM 구조 변경에 취약하고 읽기 어렵습니다. label 기반이 사람이 이해하기에도 낫습니다.

## 결과

매크로 파일이 사람이 읽을 수 있게 됩니다. `{ "label": "검색" }`은 무슨 뜻인지 바로 보입니다. 이건 디버깅과 리뷰에서 크게 유리합니다.

좌표 폴백 비중이 매크로의 취약성 지표가 됩니다. 좌표 스텝이 많은 매크로는 자주 깨질 것이라 예상할 수 있고, `stats`가 이를 확인해줍니다.
