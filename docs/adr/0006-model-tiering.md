# 0006. 역할별 모델 분리

**상태**: 탐색 계획 행은 [0010](0010-planning-on-sonnet.md)으로 대체됨. 나머지는 accepted
**날짜**: 2026-09-08

## 맥락

에이전트 루프 안에서 모델이 하는 일은 성격이 다릅니다. 어떤 건 판단이 필요하고 어떤 건 분류에 가깝습니다. 전부 같은 모델로 하면 쉬운 일에 비싼 값을 냅니다.

## 결정

역할별로 모델을 나눕니다.

| 역할 | 모델 | effort | 호출 빈도 |
| --- | --- | --- | --- |
| 라우팅 | `claude-haiku-4-5` | — | 요청당 1 |
| 탐색 계획 | `claude-opus-5` | high | 스텝당 1 |
| 스텝 복구 | `claude-opus-5` | high | 실패당 1~2 |
| 화면 판정 | `claude-haiku-4-5` | — | 스텝당 0~1 |
| 매크로 추출 | `claude-opus-5` | high | 성공당 1 |

화면 판정은 **가능하면 모델 없이** 처리합니다 — 트리에서 예상 셀렉터를 찾으면 그걸로 끝입니다. 애매할 때만 Haiku를 부릅니다.

## 이유

**빈도가 비용을 결정합니다.** 화면 판정은 스텝 수만큼 발생합니다. 20스텝 작업이면 판정이 20번인데, 계획은 20번, 라우팅은 1번입니다. 판정을 싸게 만드는 게 전체 비용에 가장 크게 작용합니다.

**난이도가 다릅니다.** "지금 화면이 재생 중인가"는 분류 문제입니다. "이 목표를 달성하려면 다음에 뭘 눌러야 하나"는 판단 문제입니다. 후자에만 Opus가 필요합니다.

**라우팅은 저지연이 필요합니다.** 사용자가 말하고 나서 반응이 시작되기까지의 시간이 라우팅 지연입니다. 여기는 정확도보다 속도가 중요하고, 틀려도 Explore로 폴백되므로 대가가 작습니다.

## 대안

**전부 Opus** — 단순하지만 판정에서 낭비가 큽니다.

**전부 Haiku** — 탐색 계획 품질이 떨어집니다. 계획이 나쁘면 스텝이 늘고, 늘어난 스텝만큼 판정 비용이 늘어서 결국 손해입니다.

**Sonnet 단일** — 나쁘지 않은 절충이지만, 판정을 Haiku로 내리고 계획을 Opus로 올리는 쪽이 같은 예산에서 더 나은 결과를 냅니다.

## 결과

프롬프트를 역할별로 따로 관리해야 합니다. 모델이 다르면 잘 먹는 프롬프트도 다릅니다.

eval에서 모델별 토큰과 비용을 따로 집계합니다. 어느 역할이 예산을 먹는지 보이지 않으면 이 결정을 검증할 수 없습니다.

컨텍스트 편집(`clear_tool_uses_20250919`)과 프롬프트 캐싱은 탐색 루프에만 적용합니다. 다른 역할은 단발 호출이라 해당 없습니다.
