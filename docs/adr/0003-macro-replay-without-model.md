# 0003. 재생 경로에서 모델을 완전히 제거

**상태**: accepted
**날짜**: 2026-09-08

## 맥락

에이전트가 같은 작업을 반복할 때, 최적화 방법은 여러 가지입니다. 프롬프트 캐싱, 더 싼 모델, 컨텍스트 편집, 스텝 병합.

전부 상수 배 개선입니다. 여전히 스텝마다 모델을 부릅니다.

## 결정

재생 경로에서 **모델 호출을 0으로** 만듭니다. 저장된 셀렉터를 코드가 직접 해석하고 실행합니다.

## 이유

문제의 본질은 "모델 호출이 비싸다"가 아니라 **"이미 아는 길을 매번 다시 찾는다"**입니다. 프롬프트를 아무리 최적화해도 이 낭비는 사라지지 않습니다.

한 번 성공한 경로는 결정적입니다. 같은 화면에서 같은 버튼을 누르는 데 추론이 필요 없습니다. 필요한 건 셀렉터 하나와 그걸 해석하는 코드입니다.

0으로 만들면 이런 것들이 따라옵니다.

- 비용이 상수 배가 아니라 **0**이 됩니다
- 지연이 네트워크 왕복에서 로컬 조회로 바뀝니다 (초 → 밀리초)
- 결정적입니다. 같은 입력이 같은 동작을 만듭니다
- 오프라인에서 동작합니다
- 테스트할 수 있습니다

## 대안

**캐싱된 프롬프트로 계속 모델 호출** — 여전히 왕복이 있고, 여전히 비결정적이고, 여전히 비용이 듭니다.

**더 작은 모델로 재생** — 왕복은 그대로고 실패 양상만 예측하기 어려워집니다.

## 결과

**매크로가 앱 업데이트에 깨집니다.** 이게 이 결정의 대가입니다. Repair 경로([execution-paths.md](../execution-paths.md))가 이 대가를 관리 가능한 수준으로 낮추지만, 없애지는 못합니다.

Repair 없이 이 결정만 있으면 그냥 매크로 녹화기입니다. 두 개가 세트입니다.

또한 재생 중에는 상황 판단을 할 수 없습니다. 예상 못한 모달이 뜨면 셀렉터가 미스나고 Repair로 넘어갑니다 — 이건 의도된 동작입니다.
