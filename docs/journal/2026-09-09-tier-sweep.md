# 2026-09-09 — 0/15는 Haiku의 실패가 아니었다

[ADR 0006](../adr/0006-model-tiering.md)은 탐색 계획을 Opus에 올렸다. 근거는 논증이었다 — 판단 문제니까 비싼 모델이 필요하다. 이제 잴 수 있으니 쟀다.

## 첫 결과

```
                             ok    p50       모델  토큰    $/런
settings-open-about          0/5   12076ms   1     0       —
settings-open-accessibility  0/5   12001ms   1     0       —
settings-search-open         0/5   12193ms   1     0       —
```

Haiku 0/15. 모델 호출 1회, 토큰 0, 액션 0.

**이대로 적었으면 ADR 0006이 옳았다고 결론 냈을 것이다.** "작은 모델은 탐색 계획을 못 한다"는 문장을 쓰기에 완벽한 표다.

트레이스를 열었다.

```
model 510 {"step": 0, "error": "400 ... This model does not support the effort parameter."}
```

내 버그다. 플래너가 `output_config.effort`를 무조건 보내는데 Haiku 4.5는 그걸 안 받는다. **모델은 화면을 본 적도 없다.**

토큰 0이 힌트였어야 했다. 능력 부족으로 실패하면 토큰을 쓰고 실패한다. 0은 요청이 거절됐다는 뜻이다. 표만 보면 두 실패가 똑같이 생겼다.

## Sonnet이 Opus를 이겼다

15/15로 같고, 계획한 경로가 태스크마다 **글자 하나까지 같고**, 40% 싸다. Opus가 산 게 없다.

ADR 0006의 대안 절에 이렇게 적어놨었다.

> **Sonnet 단일** — 나쁘지 않은 절충이지만 … 계획을 Opus로 올리는 쪽이 같은 예산에서 더 나은 결과를 냅니다.

측정된 범위에서 근거가 없다. [ADR 0010](../adr/0010-planning-on-sonnet.md)으로 뒤집고 기본을 Sonnet으로 내렸다.

## Haiku는 자기 성공을 지운다

세 번째 태스크만 갈렸다. 25수 상한에 5런 전부 걸렸다.

```
 1 tap   검색창          ok=True
 2 type  "손쉬운 입력"   ok=True   ← 목표 달성
 3 tap   "텍스트 지우기"           — "새로운 검색을 시도하기 위해"
 4 type  같은 텍스트 재입력
 5 back                            — "검색 결과가 없으므로"
 6~24 지우기 → 입력 → 지우기 → 입력 …
```

**모든 액션이 성공했다.** 실행이 아니라 완료 인식이 안 된다. 도달한 상태를 도달하지 않은 것으로 읽고, 되돌리고, 다시 한다.

[아침에 고친 Opus의 중복 탭](2026-09-09-focus-invisible.md)과 같은 문제다. 화면만 보고 "내 행동이 먹혔나"를 판단하는 것. 그때는 관찰에 정보가 없어서 모델이 알 수 없었고, 키보드 비트 하나로 해결됐다. **Haiku는 그 비트를 받고도 못 한다.** 정보 부족이 아니라 판단력 문제라는 게 이 대비로 드러난다.

ADR 0006은 이 실패 모드를 예측했고 메커니즘까지 맞췄다.

> 계획이 나쁘면 스텝이 늘고, 늘어난 스텝만큼 판정 비용이 늘어서 결국 손해입니다.

3수 → 25수, $0.017 → $0.068. **같은 ADR에서 Haiku 판단은 맞고 Opus 판단은 틀렸다.**

## 캐시가 Haiku에만 안 걸렸다

| 모델 | 호출 | 입력 | 캐시 읽기 | 캐시 쓰기 |
| --- | ---: | ---: | ---: | ---: |
| opus-5 | 40 | 31173 | 55965 | 1435 |
| sonnet-5 | 39 | 30165 | 57114 | 1503 |
| haiku-4-5 | 152 | 340835 | 0 | 0 |

원인을 추측하지 않고 쟀다. 같은 산문을 시스템 프롬프트에 넣고 두 번씩 호출:

| 크기 | opus-5 | haiku-4-5 |
| ---: | --- | --- |
| ~2200 토큰 | 걸림 | **안 걸림** |
| ~4500 토큰 | 걸림 | 걸림 |

nubi의 캐시 접두부는 약 1450토큰이다. 위 티어에는 걸리고 Haiku에는 미달이다. **싼 티어를 고르면 캐시 할인은 덤으로 따라오지 않는다.**

`isFocused`를 실기로 확인해서 살아난 게 오늘 아침이었다. 같은 습관이 여기서도 값을 했다 — "Haiku는 최소 길이가 더 길다"는 그럴듯한 문장이고, 안 재봤으면 그냥 적었을 것이다.

## API 500이 하나 섞였다

Sonnet의 open-about p95가 29557ms로 튀었다. 모델이 아니었다.

```
act   1913  tap About  ok=True
model 17715 {"error": "500 ... Internal server error"}
end   29557 {"ok": true, "claimed": false}
```

`done`을 말했어야 할 호출이 죽었는데, 두 번의 탭으로 이미 목표 화면에 있었다. 러너가 기기를 확인하고 성공으로 판정했다. **[ADR 0009](../adr/0009-runner-judges-not-executor.md)가 의도대로 동작한 사례다** — 실행기는 성공을 주장한 적이 없고, 러너가 봤다.

다만 이게 `5/5`로만 보이는 건 문제였다. `falseClaims`(주장했는데 실패)는 세면서 그 반대는 안 셌다. `unclaimed`를 추가했다.

```
⚠ 1 attempt(s) reached the goal without the executor saying so
```

성공은 성공이다. 하지만 조용히 접히면 17초의 API 오류가 p95 안에 숨는다.

## 배운 것

**실패한 측정과 측정된 실패는 다르다.** 표에서는 똑같이 0/15로 보인다. 구별하는 건 트레이스뿐이고, 구별하지 않으면 내 버그가 남의 한계로 기록된다.

오늘 세 번 다 같은 순서였다 — 숫자가 나오고, 그럴듯하고, 트레이스가 반박했다. [중복 집계](2026-09-09-counting-twice.md), [가짜 백엔드 0/5](2026-09-09-fake-covered-one-third.md), 그리고 이것. 세 번 다 **그럴듯해서 위험했다.**
