# 2026-09-09 — 포커스는 보이지 않았다

첫 Explore vs 재생 비교를 돌렸다. 30/30 성공. 그런데 검색 태스크의 p95가 32초로 p50(21초)의 1.5배였다. 5런 중 2런이 유독 느렸다.

## 트레이스

```
run_mttza3la3nbz.jsonl  31765ms
    계획  tap    — 검색창에 입력하려면 먼저 포커스
    실행  tap    {'label': '검색', 'type': 'SearchField'}  ok=True
    계획  tap    — 검색 필드에 포커스를 주기 위해 탭
    실행  tap    {'label': '검색', 'type': 'SearchField'}  ok=True
    계획  type   — 검색 필드에 포커스가 있으니 "손쉬운" 입력
    계획  done
```

같은 걸 두 번 눌렀다. 두 번째 이유가 첫 번째와 똑같다.

**모델을 탓할 일이 아니다.** 탭 전후로 모델이 받는 화면이 사실상 같았다. 요소 목록도, 해시도. 첫 탭이 성공했다는 증거가 관찰 어디에도 없다. 그 상태에서 "일단 눌러보자"는 합리적인 수다.

## isFocused는 거짓말을 한다

WDA 노드에 `isFocused`가 있다. 압축에서 버리고 있었으니 살리면 될 줄 알았다. 실기로 확인했다.

```
실행 직후     isFocused 인 요소 = 0
검색창 탭 후   isFocused 인 요소 = 0
```

검색창 원본을 직접 떠봐도 `"isFocused": "0"`이다. 텍스트를 받고 있는 필드가. **시뮬레이터 WDA는 이 필드를 채우지 않는다.**

여기서 멈추길 잘했다. 스키마에 `f` 필드를 넣는 커밋까지 갔었는데, 실기 확인 없이 통과시켰으면 항상 `false`인 필드를 프롬프트에 렌더하면서 "포커스를 알려주고 있다"고 믿었을 것이다. **되돌렸다.**

## 진짜 신호는 키보드였다

같은 스크립트로 다른 걸 셌다.

```
실행 직후     Key = 0
검색창 탭 후   Key = 35
```

키보드가 뜬다는 건 뭔가가 포커스를 가졌다는 뜻이다. 그리고 나는 이걸 이미 보고 있었다 — [키보드 노이즈](2026-09-09-keyboard-noise.md)에서 `Key` 26개가 화면 예산을 날려서 통째로 버리기로 했다.

**버린 건 맞다. 다만 1비트를 남겼어야 했다.**

```ts
const keyboard = nodes.some((n) => KEYBOARD.has(n.type));
...
if (keyboard) screen.keyboard = true;
```

키 35개는 그대로 버린다. 누를 일이 없으니까. 화면에는 한 줄이 붙는다.

```
note: the keyboard is open, so a text field has focus
```

## 해시에도 넣었다

이게 더 중요한 부분이다.

```ts
return createHash('sha1')
  .update(keyboard ? `kb\n${body}` : body)
  .digest('hex');
```

화면 해시는 "뭔가 바뀌었나"를 모델 없이 판단하는 수단이다. 그런데 **텍스트 필드를 누르는 건 요소를 하나도 바꾸지 않는다.** 키보드를 해시에서 빼면 성공한 탭과 아무 일도 안 한 탭의 해시가 같다. 압축이 정확히 그 정보를 지우고 있었다.

```
실행 직후     keyboard=false  hash=4718990ac133
검색창 탭 후   keyboard=true   hash=0fbaf8770520
입력 후        keyboard=true   hash=db0108f6ce27
```

## 결과

| | 전 | 후 |
| --- | ---: | ---: |
| p95 | 32249ms | 24178ms |
| 모델 호출 | 3~4 (런마다 다름) | 3 (전부) |
| 토큰 | 1993 | 1782 |

흔들림이 사라졌다. 5런 전부 같은 경로를 간다.

## 배운 것

[베이스라인](../benchmarks/2026-09-09-three-tasks.md)에서 검색 태스크가 제일 어려울 거라고 적었고, 그건 맞았다. **이유를 틀렸다.** 순서를 틀릴 거라고 봤는데, 모델은 순서를 한 번도 안 틀렸다. 문제는 자기 행동의 결과를 볼 수 없다는 것이었다.

압축은 토큰을 줄이는 작업이라고만 생각했다. 실제로는 **모델이 볼 수 있는 세계를 정하는 작업**이다. 버린 것 중에 상태 변화를 알리는 유일한 신호가 있으면, 모델은 그 변화를 못 본 채로 행동한다. `Key` 35개는 지금도 버리는 게 맞다. 다만 무엇을 버리는지와 **그것이 무엇을 증언하는지**는 다른 질문이었다.
