# 2026-09-09 — 계기가 자기를 두 번 셌다

첫 Explore 비교가 나왔다. 태스크당 모델 호출 4회, 6회, 6.8회.

6.8회가 걸렸다. 검색 태스크는 액션이 셋인데(탭·입력·완료) 호출이 7번 가까이 나올 구석이 없다. 트레이스를 열었다.

```
model  explore  step=0   2841ms
model  explore  step=0      0ms
model  explore  step=1   1903ms
model  explore  step=1      0ms
```

**같은 스텝이 두 번씩 있다.** 하나는 시간이 있고 하나는 0ms다.

## 원인

```ts
const plan = await trace.span('model', 'explore', {...}, () => this.planner.next({...}));
if (plan.usage) {
  trace.model('explore', plan.usage, 0, { step });
}
```

`span`이 호출을 감싸면서 `model` 이벤트를 하나 쓰고, 사용량을 기록하려고 `trace.model`이 또 하나 쓴다. 둘 다 타입이 `model`이라 집계가 2로 센다. 지연은 `span` 쪽에만 있고 토큰은 `trace.model` 쪽에만 있어서, **어느 쪽도 혼자서는 틀려 보이지 않았다.**

한 호출에 한 이벤트로 합쳤다. 시간은 직접 재고, 사용량이 없으면 0으로 채운다. 실패했을 때도 이벤트가 남도록 `try/catch`를 붙였다 — `span`이 해주던 일이라 합치면서 잃을 뻔했다.

| | 전 | 후 |
| --- | ---: | ---: |
| open-accessibility | 4 | 2 |
| open-about | 6 | 3 |
| search-open | 6.8 | 3 |

정확히 절반이다.

## 왜 안 걸렸나

트레이스 테스트는 `span`이 이벤트를 쓰는지, `model`이 사용량을 담는지를 각각 확인한다. **둘을 같이 쓰면 안 된다는 건 아무도 확인하지 않았다.** 각 부품은 명세대로였고, 조합만 틀렸다.

집계 쪽도 도움이 안 됐다. `calls`는 `type === 'model'`인 이벤트를 세는데, 이벤트가 정직하다는 걸 전제로 한다. 4든 8이든 똑같이 그럴듯한 숫자를 뱉는다.

## 두 번째다

[첫 숫자](2026-09-09-first-numbers.md)에서 p50이 67% 높게 나왔다. 셋업이 측정 구간 안에 있어서였다. 그때 이렇게 적었다.

> **첫 숫자는 대체로 틀렸다.** 14.6초는 그럴듯했다.

같은 일이 다시 일어났다. 그리고 이번에도 **그럴듯해서 위험했다** — 6.8회는 "탐색이 헤맸나 보다"로 읽히고, 그게 사실이었다면 흥미로운 발견이었을 것이다. 틀린 숫자가 말이 되는 이야기를 만들어낼 때가 제일 나쁘다.

## 배운 것

계기는 자기가 재는 대상만큼 검증돼야 한다. 여기서는 계기가 자기 자신을 두 번 셌고, 결과는 완벽하게 일관된 거짓말이었다 — 런마다 같은 배수로 틀렸으니 편차도 작고 비교도 깔끔했다.

**일관성은 정확성의 증거가 아니다.**

트레이스를 원시 이벤트로 남긴 게 살렸다. 집계만 저장했으면 6.8을 반박할 방법이 없었다. 줄 단위로 쌓인 파일을 열어 같은 `step=0`이 두 줄인 걸 보는 게 유일한 확인 방법이었다.
