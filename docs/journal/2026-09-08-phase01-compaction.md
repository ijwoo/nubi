# 2026-09-08 — phase 01: 트리 압축

## 왜 이것부터

phase 01은 Hands다. 순서를 이렇게 잡았다.

```
WDA 타입 파싱 → 트리 압축 → 셀렉터 해석 → WDA 클라이언트 → 세션 슈퍼바이저
     ↑ 순수 함수 (기기 불필요)              ↑ 여기부터 기기 필요
```

**순수 함수부터 만든다.** 트리 압축과 셀렉터 해석은 입력이 트리, 출력이 요소 목록인 함수라 기기 없이 픽스처로 전부 검증된다. 실기기 서명(무료 계정 7일 재설치)에 막혀서 진도가 안 나가는 상황을 피하고 싶었다.

## WDA 파싱에서 조심한 것

WDA는 같은 필드를 빌드에 따라 `true`, `"true"`, `"1"`로 준다. 전부 관대하게 파싱한다.

더 중요한 건 `name` 필드다. **WDA는 `accessibilityIdentifier`가 있으면 그걸 `name`에 넣고, 없으면 조용히 `label`로 폴백한다.** 이걸 구분하지 않으면 라벨을 식별자로 착각해서, 가장 안정적인 셀렉터 등급([ADR 0004](../adr/0004-selector-priority.md))에 제일 취약한 값을 등록하게 된다.

그래서 `identifierOf`는 엄격한 쪽으로 틀리게 했다 — `name === label`이면 식별자가 없는 것으로 본다. 실제로 식별자가 있는데 우연히 라벨과 같은 경우를 놓치지만, 반대 실수보다 이쪽이 낫다.

이 가정은 실기기에서 검증이 필요하다. 지금은 문서화된 추정이다.

## 테스트가 설계 결함을 잡았다

압축 규칙을 짜면서 `textOf(node)`를 만들었다. 라벨을 우선하고 없으면 값을 쓰는 함수.

검색창 테스트가 깨졌다.

```
expected '아티스트, 곡, 가사' to be '뉴진스'
```

검색창의 `label`은 플레이스홀더고 `value`가 실제 입력된 내용이다. 버튼은 라벨이 중요하고 입력 필드는 값이 중요하다 — **둘 중 하나를 고르는 설계 자체가 틀렸다.**

둘 다 필요하다. 모델이 "검색창에 이미 뉴진스가 들어있으니 지우고 다시 칠지, 그냥 진행할지"를 판단하려면 라벨(어떤 컨트롤인지)과 값(지금 상태가 뭔지)이 둘 다 있어야 한다. 스위치도 마찬가지다 — 값만 있으면 `"1"`인데 뭐가 켜졌는지 모르고, 라벨만 있으면 켜졌는지 꺼졌는지 모른다.

`Element`에 `v` 필드를 추가하고 `textOf`를 `labelOf` / `contentOf`로 쪼갰다. `contentOf`는 값이 라벨과 같으면 undefined를 반환해서 중복을 안 만든다.

테스트를 먼저 쓴 게 아니라 픽스처를 실제 화면처럼 만든 게 잡아준 것 같다. 검색창에 플레이스홀더와 입력값을 둘 다 넣어둔 게 우연히 맞았다.

## 압축 규칙

```
유지 조건:
  visible && 면적 > 0 && 화면과 겹침
  && ( 상호작용 타입              (Button, Cell, TextField, ...)
     || 텍스트가 있고 (accessible || 레이아웃 컨테이너가 아님) )

제외:
  이미 유지된 조상과 텍스트가 같고 rect가 그 안에 포함되는 것
```

두 가지가 실전에서 중요할 것 같다.

**`accessible`인 컨테이너는 살린다.** React Native나 Flutter는 커스텀 컨트롤을 `XCUIElementTypeOther`로 노출한다. 타입만 보면 레이아웃 래퍼지만 `isAccessible`이 붙어 있으면 진짜 컨트롤이다. 픽스처에 "전체 셔플" 버튼을 이 형태로 넣어뒀다.

**조상 중복 제거.** WDA는 Button 안에 같은 라벨의 StaticText를 중첩시킨다. 둘 다 남기면 요소 수가 두 배가 되고 모델에게 같은 걸 두 가지로 말할 방법을 준다.

**서브트리는 안 자른다.** 안 보이는 컨테이너 안에 보이는 컨트롤이 있는 경우가 있어서, 노드 단위로만 거른다.

## 비활성 요소는 남긴다

회색으로 죽어있는 버튼도 `e: false`로 남긴다. "다운로드 버튼이 비활성이다"는 정보다 — 왜 경로가 막혔는지 모델이 알 수 있다.

## 화면 해시

모델 없이 화면 변화를 감지하려고 요소 집합의 해시를 만든다. rect를 4pt 단위로 양자화해서, 스크롤이 1px 다르게 멈추거나 렌더링 지터가 있어도 같은 화면으로 읽는다.

이건 `assert` 스텝을 모델 호출 없이 처리하는 근거가 된다.

## 숫자

픽스처(음악 앱 검색 결과 화면) 기준.

```
원시 노드       20
압축 후 요소    10
원시 JSON       3472자
압축 JSON        724자
추정 토큰        242
```

토큰 추정치는 문자수/3인 대략값이다. 한국어 라벨이 영어보다 토큰이 많이 나오니까 나눗수를 보수적으로 잡았다. 실제 값은 나중에 count_tokens로 재야 한다.

**픽스처가 작다는 게 함정이다.** 20노드짜리 화면이고, 실제 앱 화면은 수백 노드다. 압축비(문자 기준 4.8배)가 절대값보다 의미 있는 숫자인데, 이것도 실제 트리에서 다시 봐야 한다. 600토큰 예산 테스트는 지금 통과하지만 이건 회귀 방지용이지 증명이 아니다.
