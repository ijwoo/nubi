# 2026-09-09 — 첫 숫자, 그리고 그게 틀렸던 이유

## Phase 02는 숫자를 만들 수 없다

로드맵상 phase 02는 Trace + Eval인데, 시작하면서 스코프를 정직하게 짚어야 했다.

**지금은 "학습 전/후"를 잴 수 없다.** Explore(phase 03)도 Macro(phase 04)도 없으니까. Phase 02가 만드는 건 **측정 장치**다.

그런데 장치만 만들고 비워두면 그게 동작하는지 알 수 없다. 그래서 실행기 인터페이스를 두고, **스크립트 실행기** 하나를 붙였다 — 고정된 스텝 목록을 재생하는 것. 매크로 포맷은 이미 정의돼 있으니 그걸 그대로 쓴다.

이건 phase 04 replay의 원형이지만, 매크로 추출도 자가치유도 없다. 측정 장치를 빈 채로 두지 않으려는 최소한이다.

## 판정은 실행기가 하면 안 된다

설계에서 제일 신경 쓴 지점.

```
Task     목표와 증거를 정의한다. 경로는 정의하지 않는다.
Executor 시도한다. 자기가 끝냈다고 생각하는지 보고한다.
Runner   기기에 태스크의 assertion을 직접 확인한다.
```

**실행기가 자기 성공을 판정하면 측정하는 게 실행기의 의견이다.** 러너가 별도로 확인한다.

이걸 테스트로 박아뒀다 — 무조건 `true`를 반환하는 가짜 실행기를 넣으면 `successRate: 0`, `falseClaims: 2`가 나온다. 실행기가 주장한 성공과 기기가 확인한 성공이 다른 케이스가 리포트에 드러난다.

태스크에 스텝을 안 쓰는 것도 같은 이유다. 스텝을 태스크에 넣으면 **모든 측정이 "누가 적어둔 스텝"의 측정**이 된다. 같은 목표를 다른 방법으로 도달하는 걸 비교하는 게 요점인데.

## 가짜에서 0/3이 나왔다

먼저 가짜로 돌렸다.

```
settings-open-accessibility  scripted  0/3
```

매크로는 설정 루트에서 손쉬운 사용을 바로 탭하는데, **녹화된 시나리오에는 그 전이가 없었다.** 녹화할 때 `root → general → back → accessibility` 순으로 걸었기 때문에, 루트에서 직접 가는 경로가 기록되지 않았다.

매크로가 틀린 게 아니라 녹화가 좁았다. 실기에선 되는 경로다.

**가짜는 녹화된 만큼만 안다.** 당연한 말인데 실제로 부딪히니 다르게 느껴졌다. 레코더가 있어서 다행이었다 — 레시피에 한 줄 추가하고 다시 녹화하면 끝이다.

## 실기 첫 숫자: 14.6초

```
settings-open-accessibility  scripted  5/5  p50 14579ms  p95 18270ms
```

성공률은 완벽한데 숫자가 이상했다. 트레이스를 열어봤다.

```
 1 act     4707ms  launch
 2 act     2652ms  tap
 3 assert   745ms  #ACCESSIBILITY_PLACARD
 4 assert   737ms  task assertion
 5 end    14580ms
```

**이벤트 합이 8.8초인데 end가 14.6초다.** 5.8초가 어디 갔나.

러너가 매 런 시작 전에 앱을 재시작한다(알려진 상태 보장). 그 setup이 측정 구간 안에 있었다. 앱 재시작만 4.5초 넘게 걸린다.

**모든 접근 방식이 똑같이 치르고, 아무도 선택하지 않은 비용이다.** 측정에 들어가면 안 된다. 이 상태로 phase 03에서 Explore를 재보면 Explore와 Replay 양쪽에 똑같은 5.8초가 얹혀서 **차이가 실제보다 작아 보인다.**

`Trace.beginAttempt()`를 만들어 시작점을 setup 이후로 옮겼다. setup 이벤트는 트레이스에 그대로 남긴다 — 준비 중에 죽은 런도 읽을 가치가 있으니까.

14579ms → 8787ms.

## 치환이 조용히 실패했다

고치고 다시 쟀는데 여전히 14.7초였다.

코드를 직접 열어보니 `beginAttempt()` 호출이 없었다. 스크립트로 문자열 치환을 했는데, 그 사이 biome이 근처 코드를 재포맷해서(`traced(...)` 호출이 여러 줄로 쪼개짐) **패턴이 안 맞았고, 조용히 아무것도 안 하고 끝났다.**

같은 실수를 반복하지 않으려고, 이후 치환 스크립트는 대상을 못 찾으면 종료하게 했다.

측정 도구를 고치는 중에 측정 결과로 그 수정이 안 됐다는 걸 발견한 셈이다. 트레이스가 없었으면 14.7초를 그냥 믿었을 것이다.

## 최종

```
settings-open-accessibility  scripted  5/5  p50 8787ms  p95 8942ms
                                            액션 2  관찰 1  모델 0  토큰 0
```

런 하나의 구성:

```
act     4520ms  launch (restart)
act     2925ms  tap #com.apple.settings.accessibility
assert   752ms  #ACCESSIBILITY_PLACARD
assert   741ms  task assertion
```

**탭 하나가 2.9초다.** 이 안에 `screen()`이 두 번 들어있다 — 셀렉터를 풀기 위한 관찰과 액션 후 화면. 각 `screen()`은 `/source` 덤프에 알림 확인 요청까지 붙는다.

관찰 비용이 지연을 지배한다. 최적화할 곳이 어디인지 첫 측정이 이미 가리키고 있다. 하지만 지금 최적화하지 않는다 — 비교 대상이 생기기 전에 바닥을 흔들면 비교가 무의미해진다.

**p50과 p95가 거의 같다**(8787 vs 8942)는 것도 기록해둘 만하다. 스크립트 실행은 결정적이다. Explore가 붙으면 이 격차가 벌어질 것이고, 그 격차 자체가 비교의 핵심이 된다.

## 배운 것

**첫 숫자는 대체로 틀렸다.** 14.6초는 그럴듯했다. 성공률 5/5에 편차도 작았다. 트레이스를 열어보지 않았으면 그대로 문서에 실었을 것이다.

트레이스를 먼저 만든 게 맞았다. 러너보다 트레이스가 먼저인 순서가 우연히 옳았다 — 숫자가 나온 순간 그 숫자를 의심할 도구가 이미 있었다.
