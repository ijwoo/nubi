# 2026-09-09 — 문서가 코드를 앞질러 있었다

## 계기

phase 02를 끝내고 문서를 훑었다. 코드가 빠르게 움직인 구간이라 문서가 따라왔는지 확인이 필요했다.

**따라오지 않았다.** 그것도 "조금 낡은" 게 아니라 **존재하지 않는 것을 설명하고 있었다.**

## 없는 스키마를 문서화하고 있었다

`eval-design.md`의 태스크 예시:

```yaml
setup:
  app: com.apple.Music
  state: home
assert:
  - selector: { label: "일시정지" }
    within_ms: 30000
modes: [cold, warm]
```

실제 `TaskSchema`:

```yaml
setup:
  bundleId: com.apple.Preferences
  restart: true
  settleMs: 1200
assert:
  selector: { id: ACCESSIBILITY_PLACARD }
  withinMs: 10000
scripted:
  macro: settings-open-accessibility
```

필드 이름이 다르고, `state`와 `modes`는 아예 없고, `assert`는 배열이 아니라 객체다. 이 문서를 보고 태스크를 쓰면 하나도 안 돌아간다.

설계 문서를 코드보다 먼저 썼기 때문이다. 그때는 맞았고, 구현하면서 바뀌었고, 문서로 돌아가지 않았다.

## 약속했는데 없는 기능

```
npm run eval -- --mode warm     # 존재하지 않는 플래그
출력은 두 가지 — 사람이 볼 마크다운 표, 기계가 볼 JSON.   # JSON 없음
```

`--mode`는 cold/warm을 나누는 플래그인데, 그건 Explore와 Replay가 둘 다 있어야 의미가 있다. 지금은 실행기가 하나뿐이다.

JSON 출력은 그냥 안 만들었다. 지웠다 — **비교할 실행기가 둘 이상 생기면 그때 붙인다.** 지금 만들면 소비자 없는 형식을 추측해서 만드는 것이다.

## 섹션이 중복돼 있었다

트레이스 절을 추가하면서 "리포트를 어디에 두나"와 "정직성 규칙"을 뒤에 새로 썼는데, **앞의 옛 버전이 그대로 남아 있었다.** 한 문서에 같은 제목이 두 번.

`grep -n "^## "` 한 줄로 보였다. 문서를 열어서 읽는 것보다 구조를 뽑아보는 게 빨랐다.

## 치환이 조용히 실패한다

문서 수정을 스크립트로 하는데, 오늘 두 번 대상을 못 찾고 아무 일도 안 하고 끝났다. [어제 러너에서 겪은 것](2026-09-09-first-numbers.md)과 같은 실패다.

이번엔 치환 함수가 대상을 못 찾으면 종료하게 만들어뒀다. 그래서 `macro-format.md` 수정이 실패했을 때 **파일이 안 건드려진 채로** 멈췄고, 실제 내용을 확인하고 다시 할 수 있었다.

조용히 실패하는 도구는 아무것도 안 하는 것보다 나쁘다. 했다고 믿게 만든다.

## 자동 검사를 붙였다

한 번 훑고 끝낼 일이 아니라서 검사 세 개를 스크립트로 만들었다.

```
깨진 내부 링크        1개 (템플릿 플레이스홀더 — 의도됨)
문서에만 있는 npm 스크립트   없음
문서가 언급하는 없는 경로    1개 (ADR의 계획 경로 — 의도됨)
```

ADR·journal 개수와 인덱스 항목 수가 맞는지도 확인한다. 인덱스에 안 올린 문서는 사실상 없는 문서다.

## 놓쳤던 결정 두 개를 ADR로 남겼다

문서를 대조하다 보니 **중요한 결정인데 ADR이 없는 것**이 둘 있었다.

- [0008](../adr/0008-detect-alerts-never-answer-them.md) — 시스템 알림은 감지하되 자동으로 답하지 않는다
- [0009](../adr/0009-runner-judges-not-executor.md) — 성공 판정은 러너가 하고 실행기는 하지 않는다

둘 다 커밋 메시지와 journal에는 이유가 적혀 있었지만, "나중에 이 결정을 뒤집으려는 사람"이 찾아갈 자리에는 없었다. journal은 과정이고 ADR은 결론인데, 결론만 빠져 있었다.

## 가짜가 깨져 있었다

문서를 고치고 `npm run eval -- --fake`를 돌려보니 **0/2**였다.

매크로는 설정 루트에서 손쉬운 사용을 바로 탭하는데, 녹화된 시나리오에는 그 전이가 없었다. 녹화할 때 `root → general → back → accessibility` 순으로 걸었기 때문이다.

실기에서는 5/5로 통과하니까 눈치채기 어려웠다. **기기가 있으면 가짜가 낡은 걸 모른다.**

레코더 레시피를 매크로가 실제로 걷는 경로로 맞추고 다시 녹화했다. 3/3.

부산물로 하나 알았다 — `root-again`과 `root-third`의 해시가 같다. 처음 본 화면(16요소)과 돌아온 화면(17요소)은 다르지만, **돌아온 화면끼리는 안정적이다.** 재생이 "돌아간 화면"에 의존해도 되는지에 대한 답이라 테스트로 박았다.

## 배운 것

**문서는 코드가 아니라서 깨져도 조용하다.** 타입 체커도 테스트도 문서가 거짓말하는 걸 못 잡는다.

포폴 관점에서는 더 나쁘다. 저장소를 열어본 사람이 처음 읽는 게 문서고, **거기 적힌 스키마로 뭘 해봤는데 안 돌아가면** 나머지도 안 믿게 된다.

검사를 스크립트로 만들어둔 게 이번의 실질적 소득이다. 다음부터는 단계 끝날 때마다 돌린다.
